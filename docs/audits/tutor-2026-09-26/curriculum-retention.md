# Curriculum, retention, and mastery audit (read-only)

Scope: TutorHub, tutor session completion/evaluation, curriculum launch paths, Topic-SRS, curriculum reconciliation, existing unit coverage. No source changes. Verification: `npm test -- --runInBand tests/unit/topicSrsEngine.test.ts tests/unit/tutorSrsIntegration.test.ts tests/unit/syllabusReconciliation.test.ts` passed 3 suites / 10 tests on 2026-09-26. These tests validate happy-path refresh and preservation, not evidence validity.

## Highest-priority findings

1. **P0: Targeted is treated as assessed.** `electron/ipc/tutorHandlers.ts:1046` unions every requested topic into topicsToLog; `:1055` adds every requested ID; `:1096` writes completed and `:1101` clears new-content/gap flags; `:1109` defaults to Good when no strength/struggle matches. `src/pages/tutor/TutorSession.tsx:1053` sends the full configured topic list on end. Thus ending a multi-topic session after one question refreshes and completes unvisited topics. AI failure/no key/no parse also falls through to default Good. Tests currently bless targeted-topic auto-refresh (`tests/unit/tutorSrsIntegration.test.ts:51`, `:80`). Implement evidence-backed per-topic outcomes keyed by stable IDs and student-response IDs, separate attempted/assessed/covered states, and no score/schedule update when assessment is absent or invalid. Regression tests: 5 targets, only 1 attempted; no student answer; evaluator outage; invalid JSON; hint-only interaction; skipped topic; partial answer.

2. **P0: Completion retry repeats learning updates.** `tutorHandlers.ts:1365` sets complete then awaits evaluation each call; no prior completion/evaluation guard, idempotency key, or atomic application. BKT observations, CKRF evidence, topic reps/stability all advance again if end is retried. Failures can leave completed session with incomplete learning state. Implement persisted evaluation job/status plus unique assessment event IDs and transactional application. Retries return same stored outcome. Tests: concurrent end twice, reopen complete session then end, throw between event and schedule update, failed AI then successful retry.

3. **P1: Title heuristics can update wrong topic and direct IDs bypass subject scope.** Matching uses substring/50% word overlap (`tutorHandlers.ts:1005`, `:1014`); direct-ID fallback selects any topic globally (`:1060`, `:1090`) then records session subject ID into SRS. Duplicate titles or stale IDs can corrupt topic ownership. Use validated (userId, subjectId, topicId) joins; renderer config cannot supply authoritative scope. Pass IDs from curriculum launch (`CurriculumView.tsx:564` currently sends titles; `UnifiedSubjectDetail.tsx:399` config has no IDs). Test duplicate topic titles across modules, out-of-subject IDs, stale IDs, same title renamed.

4. **P1: No distinction between studied, mastered, and retained.** `updateTopicSrsState` always adds study completion for every rating (`src/lib/memory/topicSrsEngine.ts:338`), including Again. `syncModuleCompletionStatus` considers only existence of study-log row (`tutorHandlers.ts:687`). Completion evaluator also clears gaps even on struggle. UI explicitly says 'retention updated to 100%' (`TutorSession.tsx:1083`), while model returns R(0)=1 for any rating (`topicSrsEngine.ts:308`). R(0)=1 is an internal model property, not proof the student knows the topic. Keep completion as coverage if desired but clearly label it; mastery requires demonstrated performance and retention is an uncertain estimate. Show 'review recorded; needs another attempt' for lapses, plus next review. Do not clear misconception/gap flags without remediation evidence.

5. **P1: Mastery identity and observation quality are unreliable.** `tutorHandlers.ts:846` and `:885` store AI free-text strengths/struggles as concept identifiers, update BKT and record fixed CKRF score 1 or .25 at difficulty 3. Rephrasings create multiple concepts; a concept in both lists becomes two observations. `:854` flips good→mastered but mastered→good on next positive summary. Use canonical concept/topic IDs and single structured assessment evidence with support level, correctness, difficulty, confidence, timestamp, source question. One validated event should update all downstream views. Map historical strings conservatively, retaining unmapped history. Test repeated wording changes, contradictory outcomes, consecutive success after mastered.

6. **P1: Manual uncomplete leaves stale maintenance state.** `tutorHandlers.ts:2790` deletes study log only; `getTopicsRetention` queries SRS rows regardless completion (`topicSrsEngine.ts:194`), and summary counts SRS rows as completed (`:402`). So curriculum says incomplete while retention summary says completed and may still recommend drill. Define semantic choice: unmark coverage while preserving memory (then do not equate SRS rows to completed), or explicit reset learning (separate operation). Test uncomplete after completed/backfilled/reviewed; re-complete and no history loss.

## Model, UI, and curriculum improvements

- **Scheduling preference drift:** Topic-SRS always passes DEFAULT_FSRS_PARAMS (`topicSrsEngine.ts:304`); flashcard path reads desired_retention (`electron/ipc/dbHandlers.ts:569`). Respect same effective settings or expose clearly distinct topic policy. Backfill invents stability=3 days (`topicSrsEngine.ts:148`) for manual completion, with no confidence/provenance field. Persist source=legacy/manual and low evidence confidence, invite a short calibration review rather than confidently estimating retained knowledge.
- **Dates/status:** `classifyRetentionStatus` marks nextReviewDue <= today as overdue (`topicSrsEngine.ts:94`) even at 90% retention, whereas UI colors all overdue as critical (`TutorHub.tsx:736`). Use distinct due today/overdue/fading labels and local calendar-day policy; injectable clock for deterministic tests. Invalid dates currently propagate NaN through elapsed/retention functions (`topicSrsEngine.ts:73`). Add date/rating/stability validation and boundary tests (UTC midnight, local midnight, DST, invalid stored values).
- **No-history summary:** averageRetention=1 when no memory records (`topicSrsEngine.ts:403`) is unknown, not perfect retention. Return null/unknown and evidence counts; expose studied fraction separately.
- **Maintenance UX:** Existing feature has per-class filter, six-item default, quick/recommended/open-ended drills (`TutorHub.tsx:665`). Improve into 'Review due' with due count and bounded time budget, 'Start 10-minute review', batch small topics and adaptive stop after evidence, estimated workload explanation, explicit why this topic, empty/loading/error states, no anxiety-inducing precision. Current minutes are only retention-based (`topicSrsEngine.ts:111`), no topic scope, observed recall time, or learner pace; prioritize with due date, prerequisite relevance, exam date, confidence, and effort budget, with deterministic explanation.
- **Warmups are not prerequisite-aware:** `tutorHandlers.ts:1946` labels the lowest-retention two subject topics 'prerequisite topics' but does not graph-check relevance. Use prerequisite edges and optional short warmup; avoid derailing today's goal.
- **Evaluation blind to long session tail:** transcript takes first 8000 chars (`tutorHandlers.ts:734`); late corrections, retrieval wins, and later topics disappear. Persist per-turn assessment evidence; bounded summary extraction uses evidence plus rolling summary/recent messages. Test learner initially wrong then correct late beyond 8000 chars.
- **Reconciliation preserves IDs but may relocate topic arbitrarily:** unmapped completed/card/problem topics assigned last active module (`syllabusHandlers.ts:325`). Preserve in explicit 'Unmapped previous topics' section and offer audited mapping; include SRS/evidence links in preservation conditions (currently only completion/cards/problems), especially after manual uncomplete. Existing reconciliation tests cover progress but not SRS/evidence preservation, duplicate titles, content expansion, topic split/merge.
- **Auditability:** Topic-SRS schema (`src/lib/db.ts:639`) has only latest state; add immutable topic_review_events with evidence, rating, prior/post state, session linkage, provenance/version. Required for deduplication, debugging, undoing invalid evaluation, and eventual calibration. Avoid attempting FSRS parameter tuning before trustworthy events exist.

## Suggested execution sequence for GPT-6 Sol

A. Create canonical TopicAssessment and SessionEvaluation contracts, database migration/event ledger, validation, and scope checks; introduce no-evidence outcome. Keep renderer stable initially.
B. Extract evaluation/application service from large tutorHandlers, mock AI boundary, persist retry-safe evaluation status and apply outcomes transactionally. Replace target-topic auto-credit. Fix mastery transition and implement stable concept mapping.
C. Align curriculum completion, mastery and retention semantics; manual completion/reset policy; retain legacy records with provenance. Thread stable IDs across all launchers. Update reconciliation preservation.
D. Unify effective scheduler settings/date policy; robust data validation and unknown states; derive due queue without misleading certainty. Keep FSRS math independently tested.
E. Redesign review queue around bounded budgets, explanations and batch drills; show evidence-based end summary, partial completion, retry on save failure, next best action.
F. Add integration/e2e acceptance flows across curriculum→drill→partial finish→hub→reopen; include offline/evaluator failure, duplicate finish, skip, hint/lapse, multi-user/subject IDs, renamed topic, no-history, settings changes and date rollovers.

Success criteria: untouched targets never change mastery/SRS/completion; every schedule mutation has one evidence event; retries are no-ops; exactly assessed IDs change; failed recall stays needing work; user sees actual saved status; stable IDs survive curriculum reconciliation; due list reflects settings and correct date; no-history is never represented as 100% learned.
