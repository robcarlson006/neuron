# Neuron focus/study block audit — 2026-09-26

Read-only source audit; no application code modified. Existing targeted tests: `npm test -- --runInBand tests/unit/focusBlock.test.ts tests/unit/focusBlockNav.test.ts tests/unit/calendarFocusContext.test.ts` passed 3 suites / 13 tests. These test store transitions, route strings and prompt strings, not end-to-end learning completion.

## Highest priority findings

1. **P1: Moving on can discard the tutor completion/evaluation path.** `src/App.tsx:206` uses HashRouter; `src/components/tutor/FocusBlockTimerBanner.tsx:50` detects tutor routes using `window.location.pathname`, which is `/` in dev or an HTML file path in packaged Electron, not the hash route. Its intended end-session handoff therefore does not run; lines 58–65 mark the plan complete and navigate. `FocusBlockTimeUpModal.tsx:25–44` always directly marks/advances/navigates and never calls tutor finalization. `TutorSession.tsx:1067` is the actual tutorEndSession call that records evaluation and retention effects; bypassing it means the plan can claim completion without those effects. Fix with a typed session/block coordinator, router location rather than global pathname, and one awaited idempotent finish-step command used by banner, expiry modal, early exit and tutor summary. Include retryable persistence failure and never navigate before finalized state is stored.

2. **P1: Even the intended tutor handoff does not advance to the next block step.** Banner dispatches `detail.isLastStep` (`FocusBlockTimerBanner.tsx:53`), but `TutorSession.tsx:180–184` ignores event details and just opens End Session. The summary Hub action calls `endFocusBlock(true)` (`TutorSession.tsx:1395–1399`), losing all remaining steps; no `nextFocusBlockStep` call exists in TutorSession. Store transition intent and, after evaluation/card-choice completion, continue to the actual next pending step. Summary should say “Next: …” when one exists.

3. **P1: Resume Step starts over and can resume the wrong plan item.** `TutorHub.tsx:484` calls `handleStartSprint(focusBlock.activeIndex)`, which reads *current dailyPlans* and calls `startFocusBlock` (`167–173`); this resets full duration/paused state (`appStore.ts:274–289`) and navigates a fresh tutor config route rather than saved tutor session ID (`focusBlockNav.ts:51–58`, specific-session resume only occurs at `TutorSession.tsx:277–279`). Daily plans may be reordered (completed at end), dismissed or regenerated while the active block retains the old array, so positional indexing can change identity. Resume via block/step ID and stored activity session ID, preserving elapsed time and state. Test partial progress → hub → resume, and reorder/dismiss/regenerate cases.

4. **P1: Two independent clocks contradict one another.** Block decrement is one second per callback (`appStore.ts:336–348`, timer banner:18–26); tutor uses a separate wall-clock delta and local pause flag (`TutorSession.tsx:648–676`). Pausing/extending block never pauses/extends tutor runtime, while tutor prompts receive its own `timeRemainingSeconds`/pacing (`TutorSession.tsx:598–600`). A learner can pause the banner while the tutor silently runs out of time, or extend block while tutor still thinks time is up. Main/block state is memory-only (`appStore.ts:8–17,104,272`) and lacks timestamps or activity IDs. Replace independent clocks with one persisted runtime source and an explicit sleep/pause policy. UI timers should derive display from timestamps, not count callbacks. Save block and activity identity and allow crash/reload recovery.

5. **P1: Focus-block retention drill loses the retention contract.** Deterministic planner gets `topDue` but stores only its *title* (`tutorHandlers.ts:2419–2432`), daily-plan insert only persists target_topic (`2554–2566`), and navigation creates generic duration/depth/never_studied/target_topic (`focusBlockNav.ts:51–55`). It drops topic ID, module ID, is_spaced_review and spaced_review_topics. Contrast direct Maintenance Due launcher `TutorHub.tsx:121–131`, which sets all those fields. Thus the same advertised retention drill takes a materially different teaching/evaluation route. Introduce explicit activity intent and canonical topic/module IDs; one shared session-config builder for maintenance, curriculum and plans. Tests must assert the identical retention target survives generation → DB → navigation → session → evaluation.

6. **P1: AI planner does not receive curriculum retention due data.** Only deterministic fallback calls `getTopDueMaintenanceTopics` (`tutorHandlers.ts:2419`); normal AI subjectBriefs (`2498–2513`) contain cards, old topic-memory struggles, module and deadlines, no retention metrics. Prompt priorities (`1232–1235`) omit maintenance. Consequently connecting a working AI provider can make this dimension worse. Build one ranked candidate set from canonical scheduling data, give AI constrained candidate IDs to arrange/explain, and apply the same validator for AI and fallback. Include due maintenance, uncertainty, prerequisites, upcoming exams and recent evidence. Avoid fixed flashcards-first starvation when small time budgets always consume the whole slot.

## Further actionable defects

7. **P2: Time-up and early-exit falsely imply completed learning.** Last-step modal announces “all steps completed” and “progress recorded” before any completion write (`FocusBlockTimeUpModal.tsx:57–74`); every early-end handler passes `true` (`:42–44`, timer banner:70–72). Store completion calls are fire-and-forget and errors only logged (`appStore.ts:357–359,387–395`). Model `pending/active/paused/completed/skipped/abandoned`, with learning evidence separate from elapsed minutes. Allow stop without completing and retain remaining work. Confirm persistence before celebrating. Last-step expiry currently offers no extend/stay (modal:95–141); give the same choices on every step and let learner finish their current response.

8. **P2: Completed items are included in active sprint.** Hub starts from first incomplete but passes entire dailyPlans (`TutorHub.tsx:450–454,167–173`); backend order puts completed entries last (`tutorHandlers.ts:2577–2578`); store blindly increments (`appStore.ts:364–367`). After finishing new steps the sprint can repeat old completed ones. Snapshot only pending selected items, using stable IDs. Test mixed completed/incomplete plan and all-complete case.

9. **P2: Regeneration destroys existing plan before successful replacement and invalidates running blocks.** `tutorHandlers.ts:2289–2290` deletes all unfinished plans *before* AI generation and outside insert transaction. AI malformed output/insertion failure can leave no prior plan, and active block references deleted IDs. Recalculate remains enabled during active blocks (`TutorHub.tsx:431–445`), and completion reports success even if missing row (`tutorHandlers.ts:2582–2584`). Generate/validate first, atomically version or replace nonactive plans, and preserve active step identities. Guard concurrent requests with generation version / request identity.

10. **P2: Planner input/output validation is insufficient.** Only checks a nonempty array (`tutorHandlers.ts:2537–2539`); invalid subject silently becomes subjects[0], arbitrary action_type/durations/priorities inserted (`2552–2566`). No actual finite positive duration, count, actionable-resource availability, total budget, completion duplicate or topic ownership checks. Prompt's EXACT time vs ±5 contradiction (`1231,1238`) is not enforcement. Deterministic branch may yield four items, drop residual 1–9 min, and repeat completed work because completedToday is only passed to AI prompt. Extract pure candidate/scoring/allocation functions and schema validator; reject/repair unsafe schedules deterministically, with explicit explanation when no useful work fits.

11. **P2: Calendar slot ignores date and start.** Calendar passes minutes/start/date (`Calendar.tsx:170–172`); Hub only consumes minutes (`TutorHub.tsx:80–85`) and uses today's UTC date (`61–62`), with context detector for *now*. Choosing a future slot produces an immediate plan for today and does not schedule it. Preserve local date, timezone and interval through planner, distinguish start-now from schedule, use selected-slot context, store linkage to event; validate overlap and duration. Test UK near-midnight/DST and future day selection. `new Date().toISOString().split('T')[0]` can be wrong local study day.

12. **P2: Scheduled activity promises more than destination does.** Planner post-lecture “Card Synthesis” (`tutorHandlers.ts:1208–1210`) produces action_type flashcards; navigation only opens `/study/:subjectId` (`focusBlockNav.ts:13–15`), which reviews due cards, not source-linked generation. Syllabus step only opens subject root (`focusBlockNav.ts:62–64`), not module/resource/objective. Cards also lose target_topic. Define distinct `review_cards/create_cards/learn_topic/retrieve_topic/read_material` payloads and deep-link each to correct scope. Check availability before scheduling, provide useful alternative when no cards/materials exist, and carry the learning objective to tutor prompt.
